# bili 超长会话恢复与降级设计

## 目标

让 bili 在超长历史、上游摘要失败、字节密度误判和客户端超时情况下，优先复用已有折叠成果，继续压缩或确定性裁剪过早历史，尽量完成请求；不把主动 413 当作常规恢复策略。

## 已确认的用户决策

1. 当系统提示、工具定义、当前消息或不可拆分内容本身过大时，继续降级处理；不强制转发必然失败的原始报文，也不裁掉当前任务或工具定义。
2. 历史压缩采用模型摘要优先；摘要失败、超时或预算不足时，使用确定性摘要/裁剪兜底。原文仍保留在 bili 存储中，可检索恢复。
3. 用户自行安装插件和重启 DSH；施工方只发布可安装制品，不触碰正在运行的插件和数据库。

## 设计

### A. 恢复顺序

1. 使用已持久化的折叠块，重新计算当前实际出站视图。
2. 对仍未折叠的相邻区间执行合并折叠；模型摘要成功时正常提交。
3. 摘要失败、超时或剩余调用预算不足时，对该区间使用已有 `deterministicDigest`，并保留可恢复标记。
4. 折叠后重新计算窗口。只有不可折叠且仍超窗时才进入显式降级诊断；不重复发送原始超大报文。

### B. 不拒绝的边界

“不拒绝”不等于“保证上游成功”。bili 不主动以 413 终止可由折叠修复的请求；对无法安全缩小的系统/工具/当前任务，不擅自删改任务语义。若最终仍失败，返回可诊断结果，且保留已经完成并提交的折叠成果，供下一次继续。

### C. 原生 DSH 压缩

- 裁剪历史后，根据 `window - fitted input` 恢复合理的输出预算，至少保证能产生非空摘要。
- 将 HTTP 200 且完成原因为 `length`/`max_tokens` 的摘要视为“需要继续裁剪/重试”，而非成功。
- 非流式 JSON 和 SSE 都检查完成原因；不读取正文两次，不破坏原始响应流。

### D. 增量与缓存

- 第一优先级是复用已提交块；按实际消息内容/覆盖关系确认复用，不按会话名称盲信。
- 若日志或测试证明同一未提交摘要在断线/进程切换后重复请求，再增加一个小型进程内摘要缓存，键包含模型、任务类型、长度预算和规范化内容哈希。
- 缓存只在内容、模型和输出预算完全一致时命中；不缓存失败、空摘要、截断摘要。
- 不新增持久化表，不打开运行中数据库，不引入跨会话摘要复用。

### E. 超时与保活

- 复用 `beginPreflightHold`，确认 preflight 开始前已安装、结束后停止，SSE 注释只在完整行边界写入。
- 对不经过该 HTTP 响应的原生 fetch 车道，不能靠 SSE 保活；必须限制串行摘要调用并尽快提交确定性降级，避免无限等待。
- 不新增全局超时配置项；先使用已有调用预算、轮次预算和 abort 信号。

### F. 上游错误分类

- 新增实际事故文案：`Input too long`、`input exceeds the context limit`。
- 解析 `model limit N tokens, requested M tokens`，分别用于窗口学习和重裁。
- `requires adaptive thinking` 等明确参数错误不得进入超长自愈或无标记超长的对照重试。

## 非目标

- 不修改 DSH 的 asar。
- 不改变系统提示、当前用户消息或工具定义的语义。
- 不重构整个 preflight，不新增数据库表，不做全量上游 rebase。
- 不在本计划中修复所有与本问题无关的既有测试失败。
